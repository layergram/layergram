# Layergram entropy sources

Status: **active identity and protocol-v3 operating-system entropy boundaries**

Cryptographic randomness is a trust boundary, not a property that an
application-level statistical test can prove. Layergram therefore specifies
the source, rejects configuration drift, fails closed when the source is not
available, and tests the wiring around that boundary.

The platform API contracts are documented by
[`Random.secure()`](https://api.dart.dev/dart-math/Random/Random.secure.html)
and the pinned
[`getrandom` 0.4.3 README](https://github.com/rust-random/getrandom/blob/v0.4.3/README.md).

## 1. Identity mnemonics

New BIP39 identity mnemonics are generated by `SeedService` from
`dart:math`'s `Random.secure()`. Layergram supplies its own `randomBytes`
callback to `bip39` 1.0.6 and calls `nextInt(256)` for every byte. This uses the
complete uniform byte domain `0..255`; it does not use that package version's
default callback, which calls `nextInt(255)` and excludes `0xff`.

If the platform cannot supply a cryptographically secure source,
`Random.secure()` throws and mnemonic generation stops. There is no fallback
to `Random()`, timestamps, counters, device identifiers, user input, or a
Layergram-designed pseudorandom generator.

This correction affects only newly generated 12- or 24-word mnemonics. It does
not change mnemonic parsing, BIP39 seed derivation, restoration, existing
words, passphrase identities, or the keys derived from an existing identity.

## 2. Native ML-KEM Braid entropy

The active Rust SCKA implementation obtains each exact 64-byte ML-KEM key
generation seed through `getrandom::fill`. The call succeeds with the complete
buffer or the transition fails without exposing a candidate; partially filled
secret storage is zeroized.

Layergram permits only `getrandom` 0.4.3's automatically selected
operating-system backend. `entropy.rs` contains a compile-time error for every
documented opt-in backend: `custom`, `extern_impl`, `efi_rng`, `rdrand`,
`rndr`, `linux_getrandom`, `linux_raw`, `windows_legacy`, and `unsupported`.
The crate manifest also registers these configuration values with Rust's
unexpected-configuration lint, so a release flag cannot silently select a
custom, hardware-instruction-only, legacy, raw-syscall-only, or unsupported
source.

With the pinned default configuration, `getrandom` documents these principal
platform sources:

| Platform | Default source |
|---|---|
| Linux / Android | `getrandom` syscall; documented older-kernel fallback waits for `/dev/random` readiness before `/dev/urandom` |
| Windows 10+ | `ProcessPrng` |
| macOS | `getentropy` |
| iOS | `CCRandomGenerateBytes` |

Deterministic entropy is available only through a crate-private unit-test
trait. It is not exported by the C ABI and the native backend remains
unregistered and `NOT_READY`.

## 3. Assurance boundary

These controls protect against accidental use of a predictable application
PRNG, biased byte bounds, partial-success handling, and build-time replacement
of the reviewed OS backend. They do not make an absolute claim about a device
whose operating system, hardware, boot chain, or entropy subsystem is
compromised or defective. No finite test suite can prove that an external
physical or operating-system source is perfectly random.

Before protocol-v3 activation, release engineering must verify the locked
dependency graph and compile-time backend policy on every shipped target, keep
deterministic hooks outside production exports, test failure behavior, and
obtain independent cryptographic and implementation review.
